# EcomDispute M3 语义融合评测

## 实验目标

M3 验证 LLM 提取的用户主张和客服承诺能否作为 Evidence Fusion 的正式输入，而不是只作为旁路分类结果。模型为每条语义输出结构化 `statement_type`，确定性代码再将可核验的客服承诺与退款、支付事实比对。

## 数据与运行

- 模型：`gpt-5.4-mini-2026-03-17`
- 案例：40 个固定退款案例，其中人工编写 21 个、规则生成 19 个
- 场景：多轮对话、模糊表达、错误客服承诺、未发起、处理中、到账超时、跨源冲突、证据缺失和历史政策
- LLM 调用：40 次，每案一次，不选择性重跑
- 输入 Token：194,366
- 输出 Token：3,436
- 模型累计延迟：223,020 ms

## Oracle 审计

模型首轮运行完成后，原始口径为 29/40。人工检查发现 5 个 Oracle 标签过窄：

- “钱好像退回来了，麻烦看下”应允许 `verify_status`，不应强制 `refund_completed`。
- “退款页面与银行卡记录不一致”可合理归为 `refund_amount_mismatch`。
- “按申请时七十二小时政策处理”更接近 `other`，并非明确等待建议。
- “已为您申请退款”表示提交申请 `refund_requested`，不能等同资金退款已发起。
- “退款申请超时未处理”至少明确表达已申请，不足以证明资金退款未发起。

修订 Oracle 后使用同一批原始 LLM 输出重新计分，没有再次调用模型。原始首轮 JSON 和审计后计分 JSON 分开保留。

## 剩余失败

| 案例 | 失败表现 |
|---|---|
| `refund_complete_006` | 已解决的退款会话被路由为 `other`，暴露 `dispute_type` 同时承担业务域和争议存在性两个语义的问题 |
| `refund_conflict_001` | 客服复合句只提取了等待建议，漏掉“页面显示已退款” |
| `refund_overdue_002` | 将用户的超时处理投诉误标为 `wait_advice` |
| `refund_overdue_003` | 提取“未到账”，但漏掉同一句中的“处理中超过六天” |
| `refund_pending_005` | 提取查询意图，漏掉“页面仍在处理中” |
| `refund_within_002` | 将“无退款记录”误标为 `refund_not_received`，混淆未发起与未到账 |

## 工程结论

结构化客服承诺已经真实参与融合：当客服声称退款已发起、处理中或已完成，而业务系统不存在对应记录时，系统生成 `conversation_fact_conflict` Finding。负向查询也拥有独立 Evidence ID，例如 `query:refunds:<order_id>:v1`，因此“未查到记录”不再是无引用结论。

这 40 个案例仍是人工与规则构造数据，不能表述为线上准确率。下一步应拆分 `business_type` 与 `has_dispute`，并允许一个消息产生多个原子 statement，针对剩余 6 个失败做固定回归评测。
