# EcomDispute 简历与面试表达

## 简历项目名

**EcomDispute - 基于可插拔 Skill 的电商售后争议证据化诊断系统**

## 简历文案

- 设计“稳定 Harness + 可插拔 Skill”诊断架构，以 CaseState Reducer 管理对话主张、业务事实、政策版本、时间线和执行轨迹；实现 Refund 与 Delivery Delay 两个 Skill，并按 Skill 收窄订单、支付、退款、售后、物流和政策工具权限。
- 将 LLM 对话输出建模为 `business_type`、`has_dispute`、多标签 `statement_types` 和 `temporal_status`，通过确定性 Evidence Fusion 完成政策时效计算、跨源事实对齐、客服承诺核验、负向查询引用和人工复检分流。
- 构建 60 个固定人工/规则案例并使用真实 `gpt-5.4-mini` 评测：业务类型、争议识别、责任方和复检分流均为 60/60，用户/客服语义类型召回分别为 95.7%/96.7%；在 20 案例对照中，Hybrid 裁决 20/20，单 Agent Function Calling 为 14/20，输入 Token 降低约 56.9%。

> 数据均为人工编写或规则生成，不表述为线上准确率或真实业务处理量。

## 一分钟介绍

EcomDispute 解决的是电商售后争议中“对话说法、业务系统事实和政策版本不一致”的问题。系统输入会话与订单号，LLM 只负责提取用户主张、客服承诺、业务类型和时态；Harness 按 Refund 或 Delivery Skill 调用受限的只读工具，Reducer 把结果投影成 CaseState，最后由确定性 Evidence Fusion 计算政策时限、检查跨源冲突并生成建议裁决。这样保留了模型对自然语言的理解能力，同时避免让模型直接计算时间或凭空合并证据。

## 为什么采用 Hybrid

真实对照中，单 Agent 可以稳定完成 Function Calling，20 个案例共执行 100 次工具调用且没有伪造 Evidence ID，但仍会算错政策时间、混淆退款阶段或让客服话术覆盖系统事实。Hybrid 把这些可计算约束交给代码，在同一批案例上从 14/20 提升到 20/20，同时输入 Token 从 216,619 降至 93,466。

## 最值得讲的失败案例

`refund_historical_policy_001` 中，单 Agent 查询到了正确的旧政策 v1，却把 50 小时误算成超过 72 小时，错误判定平台超时。Hybrid 由代码选择事发时有效政策并计算时间差，因此得到正确结论。这个案例说明“引用了正确证据”不等于“推理一定正确”，Evidence grounding 与确定性约束需要同时存在。

## 当前限制

- 60 个案例不是线上数据，指标只反映固定人工/规则集。
- LLM 对未来、当前和完成时态仍可能混淆，因此 Fusion 只对时态明确的承诺生成硬冲突。
- 系统只输出建议裁决，不调用退款、扣款或账户写入接口。
- 当前控制台是本地只读 Demo，未实现登录、批处理 Worker 和多人复检队列。
